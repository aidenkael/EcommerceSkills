### P0-1：物流默认规则与基线冲突 ✅

**问题**：代码和测试使用固定服务费 36 元、尾程 0 元；基线要求 6 元 + 40 元。

**修复**：
- `database/db_manager.py`：`DEFAULT_CONFIG` 改为 `{"fixed_service_fee": "6.0", "default_tail_haul": "40.0"}`
- `config/config_manager.py`：属性默认值同步修改
- `database/db_manager.py`：新增 `_migrate_config()`，检测旧数据库中的出厂默认值（36/0）并自动更新为 6/40
- 已手动删除旧数据库文件，确保新 DB 从正确默认值启动
- 测试 `test_config_defaults` 和 `test_config_migration` 验证正确

> **审查要点**：打开已有旧数据库（如有），检查 config 表 fixed_service_fee 和 default_tail_haul 是否自动变为 6/40。

### P0-2：缺失费用被当成 0 → 虚假利润 ✅

**问题**：`total_logistics_cost()` 和 `total_cost()` 将 `None` 按 0 累加。用户只填成本 10 元、国内运费 5 元、售价 100 元但不填包装尺寸时，界面显示利润 49 元（实际头程未知）。

**修复**：

1. 计算层（`product_page.py` `_do_recalculate()`）：
   - 追踪 `_partial` 标志：头程无法计算 → 标记物流成本和总成本为 partial
   - 当 `log_partial == True` 时，利润/利润率/建议售价显示"数据不足(物流费用不完整)"

2. 显示层（`_set_result()`）：
   - 完整计算：显示 `350.00 元`
   - 部分计算：显示 `≥46.00 元(估算)`（仅显示已知部分作为下限）
   - 完全缺失：显示 `数据不足(物流费用不完整)`

3. 示例场景：
   - 填成本=10, 运费=5, 售价=100, 但不填尺寸重量
   - 头程费用 → 数据不足
   - 总物流成本 → `≥46.00 元(估算)` （6+40=46）
   - 总成本 → `≥51.00 元(估算)` （10+5+46=51，标记估算）
   - 利润 → `数据不足(物流费用不完整)`

> **审查要点**：只填成本和售价、不填包装尺寸，查看利润是否显示"数据不足"而非确定数字。

---

### P0-3：推广预留比例联动错误 ✅

**问题**：`_last_modified = "promo_rate"` 但计算逻辑只处理 `target_rate`、`price_rmb`、`price_usd`。用户修改推广比例后进入 `else` 分支，利润、利润率、建议售价全部清空。

**修复**：
- 新增 `_calc_direction` 变量（`"price"` 或 `"rate"`），独立追踪计算方向
- 价格修改 → `_calc_direction = "price"`
- 目标利润率修改 → `_calc_direction = "rate"`
- 推广比例修改 → 不改变 `_calc_direction`，仅触发在当前方向下重算
- 计算分支按 `_calc_direction` 判断，不再依赖 `_last_modified`

> **审查要点**：输入目标利润率 → 看到建议售价 → 再输入推广比例 → 建议售价应重新计算，不是清空。

### P0-4：目标利润率覆盖当前售价 ✅

**问题**：修改目标利润率不仅更新建议售价，还把建议售价写入"当前售价人民币"输入框，覆盖用户已输入的售价。

**修复**：
- `_do_recalculate()` rate 方向：`suggested_price_from_rate()` 结果只写入 `_set_result("suggested_price", ...)` 标签
- 删除了 `self._var_price_rmb.set(...)` 写入输入框的代码
- 用户已填的售价不受影响
- 如果用户同时还填了售价，实际利润仍基于用户填写值计算

> **审查要点**：已有售价 → 修改目标利润率 → 输入框中的售价应保持不变。

### P0-5：历史商品被当前费率重新计算 ✅

**问题**：打开旧商品时，`_load_data` 后调用 `recalculate()`，用当前配置重新计算头程和美元价格，覆盖了保存时的值。

**修复**：

1. **数据库层**：
   - `product_snapshots` 表新增 `exchange_rate`、`head_haul_rate`、`fixed_service_fee`、`rule_version` 列
   - `save_snapshot()` 接受 `rules` 参数，保存当时的费率
   - `get_snapshot()` 返回 `_snapshot_exchange_rate` 等字段
   - 旧表自动通过 `_add_column_if_missing()` 补列

2. **UI 层**：
   - `load_product()` 不再自动调用 `recalculate()`
   - 设置 `_historical_mode = True`
   - `_check_rate_changes()` 对比快照费率与当前费率，有差异时显示橙色提示条
   - 提示条格式：`"历史记录 | 费率已变更: 汇率: 7.20→7.50, 头程: 100→120元/kg | 点击「用当前费率重算」更新"`
   - 用户修改任何字段 → 退出历史模式 → 用当前费率重算
   - 新增「用当前费率重算」按钮，用户主动触发全量重算

> **审查要点**：保存一个商品（头程 100 元） → 修改头程单价为 120 → 重新打开旧商品 → 头程应显示 100 元，且显示费率变更提示条。

### P0-6：清空按钮误覆盖旧记录 ✅

**问题**：`clear_form()` 不清除 `_product_id`。用户打开旧商品 → 点清空 → 填新数据 → 保存 → 实际更新了旧记录（不是新建）。

**修复**：
- `clear_form()` 第一行增加 `self._product_id = None`

> **审查要点**：打开历史商品 → 点清空 → 保存 → 数据库应新增一条记录（不同 ID），旧记录不变。

### P0-7：缺少数据库迁移机制 ✅

**问题**：只有 `CREATE TABLE IF NOT EXISTS`，没有 schema version 或迁移脚本。以后加新字段会出错。

**修复**：
- 新增 `schema_version` 表，记录当前版本（初始 = 1）
- `_add_column_if_missing(conn, table, column, col_type)` 方法：安全补列
- `_migrate_config()` 方法：配置值迁移
- 后续阶段只需：增加版本号 → 在 `_init_db` 中写迁移逻辑
